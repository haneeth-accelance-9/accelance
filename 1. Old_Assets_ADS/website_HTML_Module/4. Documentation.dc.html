How the governed-agent architecture works

Written for the people who evaluate, integrate, and operate — not the people who pitch.

Contents

1 · The governance model

Every action an Accelance agent can take is classified into one of three tiers at design time. The tier is a property of the action type, not of the individual run — an agent cannot promote its own action to a lower-friction tier.

action:
  type: reassign_invoice_approver
  tier: review_required        # autonomous | review_required | mandatory_approval
  approvers: [ap-ops-leads]
  audit: always                # not configurable
  reversible: true

The audit: always line is the architectural invariant: there is no configuration in which an action executes without writing to the trail.

2 · The confirmation card

Review-required and mandatory-approval actions surface to approvers as a confirmation card: the proposed action in one sentence, the agent's reasoning underneath, and an expandable audit trail. Approve and Reject are the only mutating controls.

3 · Integration surface

Agents integrate with your systems of record through their existing interfaces — ERP and CRM APIs, event streams, and RPA connectors. The agentic layer holds no shadow copy of your data.

  • Read paths — event logs and API reads; used for mining, assessment, and agent context.
  • Propose paths — draft changes staged outside the system of record until approved.
  • Write paths — executed only after the tier's approval condition is met; always reversible where the underlying system allows it.

4 · The audit trail

Each entry records the action, tier, agent identity, approver identity (where applicable), timestamps, and outcome. Entries are append-only. Rejections record the optional human-supplied reason.
